# Race-loop implementation status

## Progress core contract

`blur_sim::step(State, Input) -> State` contains a deterministic, data-driven progress tracker. A caller supplies validated `RaceRules` containing a lap count and the ordered checkpoint IDs for one lap. The caller can send one explicit `RaceEvent` per step (`Start`, the next `Checkpoint`, or `LapLine`). The tracker ignores events that arrive in the wrong phase or out of order, completes a lap only after the configured checkpoint sequence, and enters `Finished` after the configured lap count.

`State::with_course` also accepts explicit planar `CourseGates` whose checkpoint IDs must match the rules in order. A gate is a directed finite segment. `Input.motion` supplies the previous and current vehicle positions for one caller step; `step` detects a forward crossing only for the next expected gate, inside that gate's width. Explicit events take precedence when supplied. The gate geometry is a project-side detector contract, not an observation of Blur's checkpoint shape or coordinate basis. It does not infer gates from installed levels.

`blur_sim::surface::SurfaceMesh` is a generic indexed triangle query. It validates finite source positions and index bounds, builds an XZ spatial tree, and returns the highest triangle hit at or below a supplied Y position. Synthetic tests cover layered and sloped surfaces, off-mesh misses, invalid inputs, and traversal across multiple tree leaves. It does not classify triangles as road/collision or implement a vehicle response. The diagnostic `blur-app --surface-probe <route|stream> <id> <x> <from-y> <z>` or `--surface-probe buffer <id> <x> <from-y> <z> <radius>` runs this query against source candidates; a hit is a candidate geometric intersection only.

This is a project runtime contract tested with synthetic inputs. It is **not** claimed to match Blur's race rules, event timing, checkpoint semantics, or start procedure. It contains no guessed default lap count, map data, physical timestep, handling parameters, collision, or event detector. No local map currently has `RaceRules`, a verified start, or a verified checkpoint sequence, so this change does not make any map playable.

## Configured vehicle motion

`State::with_vehicle` can now attach a generic planar vehicle to the same `blur_sim::step(State, Input) -> State` funnel. The caller must supply every kinematic parameter: seconds per step, acceleration, braking, drag, maximum speed, and turn rate, plus an initial pose and speed. `Input.controls` carries bounded throttle, brake, and steering values. A running step advances the vehicle, uses that exact movement for the existing directed gate detector, and then updates checkpoint/lap state. External `Input.motion` remains available for callers without active vehicle controls; an explicit race event still takes precedence. Grid and finished states do not move the vehicle. Nonfinite, negative, or out-of-range configuration/state/controls are rejected or ignored, and a numerically overflowing step leaves the vehicle stationary.

**VERIFIED (synthetic deterministic tests, 2026-10-30):** fixed caller-provided values produce repeatable vehicle positions and race state, including checkpoint and lap-line crossing, acceleration, braking, speed cap, phase gating, invalid input, and replay. **UNKNOWN:** original Blur timestep, acceleration, steering, tire response, collisions, drift, power-ups, and per-vehicle parameters. The generic vehicle has no verified map spawn or road contact. The later interactive viewer uses arrow-key controls, but this does not make a level playable.

## Interactive generic vehicle preview

`blur-app --level-preview <id> <center-x> <center-z> <radius> --drive <marker-y> <heading> <dt> <accel> <brake> <drag> <max-speed> <turn-rate>` now routes arrow-key controls through `blur_sim::step` and follows a visible direction marker. Every motion parameter, spawn center, and marker height is caller supplied. The preview uses a synthetic one-lap state solely to start the generic vehicle; no level race rules or gates are inferred. The marker is drawn over candidate geometry for visibility and does not collide with it. A headless Tokyo capture and invalid-config rejection were checked on 2026-10-30. This is a control/render integration, not a playable Blur map.

The level preview can also show caller-configured connected, nearly horizontal source components with `--surface-components <min-y> <max-y> <min-up> <max-edge> <weld-grid> <keep-largest>`. The selector uses only source geometry at runtime and can be combined with the generic vehicle marker. Its thresholds are diagnostic choices, not recovered road rules. The resulting surface has no collision response or verified course continuity.
